# Как мы разогнали e-ink дисплей до предела

*История оптимизации SSD1675A на nRF52832 — от 762 мс до 112 мс на кадр*

Метки достоверности:
- ✓ — подтверждено измерениями на железе
- ~ — гипотеза с физическим обоснованием (не опровергнута)
- ? — не перепроверено / неоднозначно

---

## Пролог: что у нас было

Устройство — e-ink «умные часы» на nRF52832, дисплей SSD1675A (128×296, BWR — чёрный/белый/красный).
Основная задача: анимации в режиме заставки. Game of Life, прыгающий шарик, бегущий текст.
Первая проблема стала очевидна сразу:

> **762 мс на один частичный кадр. Game of Life при этом — 1.3 кадра в секунду.**

Это не анимация. Это слайд-шоу.

---

## Глава 1. LUT — таблица, которую никто не читал

SSD1675A работает через Lookup Table — 70-байтный массив, задающий форму сигнала на пикселях.
Пять строк (LUT0–LUT4) описывают напряжения для пикселей: чёрный, белый, красный (×2), VCOM.
Каждая строка — семь 8-битных байт с 2-битными парами:
`00` = VSS (0В), `01` = VSH1 (+15В), `10` = VSL (−15В), `11` = VSH2 (+5В, только для красного).

Проблема была в том, что даташит описывает **два режима выбора строк LUT**:
- Режим 0 (по умолчанию): строка выбирается по переходу пикселя (было → стало).
- **Режим 1 (0xC7)**: строка выбирается по текущему значению в RAM: `{red_ram, bw_ram}`.

Мы работали с режимом 1. Это значит: LUT0 = пиксели, которые сейчас BLACK в BW RAM.
LUT1 = пиксели WHITE. LUT2/LUT3 = пиксели RED. ✓ (подтверждено поведением дисплея)

Первые несколько «оптимизированных» LUT либо ничего не обновляли (пустые строки),
либо делали весь экран серым (неправильный сигнал). Причина — перепутаны строки LUT.

### Решение

Минимальная рабочая LUT для чёрно-белой анимации:
- LUT0: `0x55` — VSH1 (+15В) на всю фазу → чёрные пиксели притягиваются к нижней пластине ✓
- LUT1: `0xAA` — VSL (−15В) → белые пиксели уходят к верхней пластине ✓
- LUT2–LUT4: нули (красный и VCOM не трогаем)
- Timing: TA=7, TB=7, RP=0 → **14 фреймов**

```
55000000000000 AA000000000000 000000000000000000000000000000000000000000000000000000
0707000000 0000000000 0000000000 0000000000 0000000000 0000000000 0000000000
```
✓ Подтверждено пользователем: "работает, ghosty, но приемлемо для анимации"

## Глава 2. Парадокс: короткая LUT = медленнее?

После написания «турбо» LUT на 14 фреймов (~112 мс волна) мы столкнулись с неожиданным:

- **Game of Life** (BALANCED LUT, ~384 мс волна): **406 мс/кадр** ✓
- **LTEST** (TURBO LUT, ~64–112 мс волна): **762 мс/кадр** ✓ (измерено, позже 630 мс после правок)

Более короткая LUT — и кадр в полтора раза медленнее? Как так?

### Гипотеза: разрядка бустерных конденсаторов ~

SSD1675A питает пикселей через пару ±15В конденсаторов (буст-конвертер).
Цикл обновления выглядит так:
1. `Enable CLK + Analog` (0xC0) — заряд конденсаторов до ±15В. **Дорого: ~600 мс.** ~
2. LUT волна — собственно обновление пикселей.
3. `Disable CLK + Analog` (0xC3) — конденсаторы начинают разряжаться.

При длинной LUT (384 мс) конденсаторы остаются заряженными бо́льшую часть цикла.
К следующему кадру они ещё частично заряжены → шаг 1 следующего кадра короче. ~

При короткой LUT (112 мс) конденсаторы разряжаются почти полностью за межкадровый интервал.
Следующий `Enable Analog` начинает с нуля → **дольше заряжается**. ~

> **Вывод**: без стриминга более короткая LUT парадоксально даёт более длинный кадр,
> потому что плата за HV-заряд платится заново каждый раз.

Это объясняет разницу 406 мс vs 762 мс. ~ (физически обосновано, прямым измерением не верифицировано)

## Глава 3. SPI — 42 мс, которые лежали прямо под ногами

Пока разбирались с LUT, заглянули в `soft_spi.c`.
Между каждым битом стоял `k_busy_wait(1)` — активное ожидание 1 мкс.
Один кадр = 4736 байт = 37888 бит = 37888 вызовов busy_wait.

До: ~850 КГц → **~44 мс на передачу кадра** ✓ (измерено через осциллограф)
После удаления wait: ~6 МГц → **~2 мс на передачу кадра** ✓

Итог: минус ~42 мс с каждого кадра. Бесплатно, одна строка кода. ✓

## Глава 4. Стриминг — HV заряжается один раз

Идея пришла из даташита: команда `0xC0` (Enable CLK + Analog) и `0xC3/0xC4` (Display Mode)
можно разделить. Если держать аналоговую часть включённой между кадрами:

```
Кадр 1: 0xC0 (заряд HV ~600мс) → загрузить пиксели → 0x04 (Display Mode 1, без HV цикла)
Кадр 2: загрузить пиксели → 0x04
Кадр 3: загрузить пиксели → 0x04
...
Завершить: 0x03 (Disable)
```

Время ожидания BUSY на 0x04 = только время LUT волны, без заряда HV. ✓

| Режим              | Первый кадр | Последующие кадры |
|--------------------|-------------|-------------------|
| Без стриминга      | ~760 мс     | ~760 мс           |
| Со стримингом      | ~760 мс     | ~112–271 мс       |

Реализация: `ssd1675a_begin_streaming()` / `ssd1675a_update_frame_stream()` / `ssd1675a_end_streaming()`. ✓

Стриминг был сначала применён только в `cmd_anim`. GoL и LTEST его не использовали — это была ошибка.
После добавления auto-streaming в `display_manager_update_partial()`:
- GoL: 406 мс → **271 мс/кадр** ✓
- LTEST: 762 мс → **800 мс** ... подождите.

## Глава 5. Осциллятор — ошибка в 2 раза

LTEST стал медленнее? Нет. Мы просто неправильно считали время.

Изначально предполагалось: осциллятор SSD1675A работает на **125 Гц** → 8 мс/фрейм.
Тогда 14 фреймов = 112 мс. Казалось разумным.

Пользователь измерил GoL с CLEAN LUT (18 фреймов по даташиту):

> **271 мс / 18 фреймов = 15 мс/фрейм → осциллятор ~67 Гц** ✓

Реальная частота — **вдвое меньше ожидаемой**. Это означает:
- TURBO 14f → не 112 мс, а **210 мс** ~
- BALANCED 100f → не 800 мс, а **1500 мс** ~

Все предыдущие расчёты нужно умножать на 1.875 (≈ 125/67). ~ (точное значение осциллятора не подтверждено прямым измерением, выведено из 271 мс / 18f)

Почему GoL показал 271 мс, а не ~210 мс при 14 фреймах?
GoL использует BALANCED LUT с другим числом фреймов — это другой пресет. ✓

## Глава 6. Призраки — когда оптимизация стреляет в ногу

После нескольких часов тестирования GoL в режиме стриминга пользователь увидел:

> «На дисплее отпечаталась GoL с временем... что не затирается даже командой CLEAN.
> Будто мы выжгли экран.»

Это не выжженный экран. Это **DC-несбалансированность** (DC offset). ~

Режим стриминга держит HV включённым и гоняет одни и те же LUT (VSH1 для чёрных, VSL для белых).
Тысячи кадров с однонаправленным полем → микрокапсулы с пигментом поляризуются в одну сторону. ~
Диспергатор устаёт удерживать частицы в нужном распределении. ~

Симптомы:
- Видимый «отпечаток» предыдущего контента на чёрном или белом фоне ✓
- Команда CLEAN (7 циклов B/W/R) не помогает ✓ — слишком мало итераций

### NUKE: принудительный сброс

Решение: команда `NUKE:N` запускает N циклов полного обновления (B → W → R) с v5-balanced LUT.
Каждый цикл: заряд HV → обновление до чёрного → до белого → до красного → разряд.
Все три цвета чередуются, нейтрализуя накопленный DC offset. ~

```
NUKE:20  — ~15 минут, для тяжёлых случаев
NUKE:5   — ~4 минуты, для лёгких артефактов
```

✓ Пользователь использовал NUKE для восстановления дисплея после ghost burn-in.

Дополнительная защита: авто-refresh каждые 500 стриминговых кадров.
Стриминг прерывается на один `0xC7` цикл с полным HV зарядом → резкое обновление → стриминг продолжается. ~
При 271 мс/кадр: 500 кадров ≈ 2.25 минуты между профилактическими обновлениями. ~

## Глава 7. Итоговые пресеты

После всех экспериментов — четыре пресета:

### MODE:0 — TURBO

Минимальная однофазная LUT. 14 фреймов. Только B/W (красный не поддерживается).
Hex: `55000000000000AA000000000000...0707000000...`
Назначение: анимации (GoL, bouncing ball). Используется со стримингом. ✓
Качество: ghosty (видны артефакты предыдущего кадра), но достаточно для движения.

### MODE:1 — BALANCED

Двухфазный пресет: пре-erase (обратный сигнал 12f) + основной drive (100f). Красный поддерживается.
Назначение: качественное частичное обновление когда нужен контраст. ~ (не тестировалось на железе в новом варианте)

### MODE:2 — STABLE

Оригинальный пресет ~1.1 с. Без изменений. Используется как baseline.

### MODE:3 — CLEAN

Ссылается на `lut_data_default` — тот же LUT, что и при полном обновлении (v5-balanced).
Самый чистый результат для одиночного partial, но медленный (~271 мс, как измерено). ✓

## Эпилог: что не стали трогать

- **BLE/NUS**: команды работают, скорость не критична. Не оптимизировалось.
- **Screensaver thread**: Zephyr семафор + k_sem_take с таймаутом — работает без изменений.
- **Red buffer**: `ssd1675a_display_buffer_fast()` не пишет Red RAM (экономия SPI) — намеренно.
  Для LTEST используется `ssd1675a_display_buffer()` (обе плоскости). ✓
